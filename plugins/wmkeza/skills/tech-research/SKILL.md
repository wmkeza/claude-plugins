# tech-research

新しめのツール・サービス・機能・ライブラリ・概念について「調べて／何？／違いは／概要」と聞かれたときの、調査から要約までの定型ワークフロー。出力はチャット内のフラットな日本語にまとめる。

## 調査手順

### 0. 型を決めてから調べ始める

型は、調べる量と出力の形を先に決めるためのもの。答えの本文には型の名前を書かない。

回数の目安は **Web検索ツールの呼び出し回数**（web_search / WebSearch など、環境によって名前が違う。以下「Web検索」）。ページ取得ツール（web_fetch / WebFetch など。以下「fetch」）は別勘定で、fetch が塞がれて試行が膨らんでも、検索の回数は独立して満たす。

- **確認型**（「Xって何？」「まだあるの？」「最新版は？」「まだ活発？」）
  確かめる実体1つにつき Web検索 1〜2回。5b で実体が複数見つかったら、並べる実体ごとに数える（それぞれの裏を取るため）。
- **比較型**（「XとYの違い」「どっちがいい？」）
  先に比較軸を決め、対象ごとに別々に検索する（1クエリにまとめると全対象が表面的になる）。Web検索は 対象数 × 1〜2回。
- **深掘り型**（「詳しく調べて」「概要をまとめて」）
  Web検索 5〜10回。加えて一次ソースの fetch が**成功3件以上**。届かなければ届かなかったと書く（試行回数を成功件数の代わりにしない）。
- **不明型**（対象が特定できない／聞き間違いの疑い）
  候補列挙で止め、手順 5a へ。

型は、ユーザーが求めている答えの量で決める。型が決めるのは出力の形で、読む量を選んでいるのはユーザーだから。「要点だけ」「ざっくり」なら確認型、「詳しく」「まとめて」なら深掘り型。どちらの言葉もなければ、対象が1つで答えが数行に収まるなら確認型、複数の観点を並べる必要があるなら深掘り型。

**停止条件**：新しい検索が既出の情報しか返さなくなったら止める。深掘り型でも Web検索 15回程度を上限とする。

調査の途中で型が変わったら、**型を決め直してから続ける**（例：確認型で調べ始めたが、対象が存在しなさそうだと分かった → 不明型に切り替える）。

### 最新性の照合（全ての型で必須）

1. 最新版・現行の仕様・存在の有無は、今日の日付（システムプロンプトか `date`）を確かめたうえで、このセッションで取得した**一次情報**（レジストリの latest、Releases、公式リリースノート）で照合する。二次情報より一次情報を優先し、学習データの記憶・過去の調査結果・検索スニペット・アーカイブなどのキャッシュは根拠にしない。
2. 記憶している版を検索語に入れず（「X latest release」のように当てる）、記憶と食い違ったら取得した一次情報を採る。
3. 「存在しない」と断定せず、「<確認日>時点で、<確認した場所>には見つからなかった」と書く。

### 1〜5. 手順

1. **Anthropic製品なら product-self-knowledge を先に確認**（利用可能なら）。Claude Code / Claude API / claude.ai の機能・プラン・モデル名・価格・要件は記憶で答えない。product-self-knowledge を見た場合も、最新性の照合は一次ソースで別に行う。

2. **Web検索**：英語クエリ＋今日の日付の年（直近の話題なら月も）。1〜2語で広く当ててから絞る。複数の角度で。

3. **一次ソースを fetch で取る**。Web検索はスニペットしか返さない。次のときは型に関わらず必ず fetch する。
   - (1) バージョン・モデル名・ホスト名・数値を答えに含めるとき
   - (2) 検索結果を根拠に断定するとき
   - (3) ユーザーが URL を渡したとき

   **fetch が失敗したときの扱い**：
   - 同一 URL へのリトライは1回まで。
   - **別ホストで同じ原本を取るのは再試行ではない**。推奨される回避路で、序列の段は下がらない。
   - 内容の異なる別ソースに乗り換えた場合は段が下がる。降格表現の対象になる。
   - どの経路でも届かなければ、届かなかったと明示し、スニペットだけで書ける範囲を書く。

   **「同じ原本」かどうかは、元のページの著者が書いた文字列がそのまま入っているかで決める。**

   | 取得したもの | 判定 | 段 |
   |---|---|---|
   | 公開ページのソースファイル（リポジトリ内の `docs/*.md`、`*.mdx` など） | 同じ原本 | 下がらない |
   | 同じページのアーカイブ・変換ミラー（web.archive.org、リーダープロキシ） | 同じ原本（ただし最新性の照合には使わない） | 下がらない |
   | パッケージレジストリ・API の生データ（`registry.npmjs.org` など） | 同じ原本 | 下がらない |
   | 同じサイトの別ページ（`/blog/x` が 403 → `/docs/y`） | 別ソース | 下がる |
   | 開発元の別リポジトリ・実装例リポジトリ | 別ソース | 下がる |
   | 第三者の要約・解説記事、検索スニペット | 別ソース | 下がる |

   fetch が塞がれている環境では、`curl` や `git clone` で同じ原本を取ってよい。**取得手段ではなく中身で判定する。**

4. **正式名称・バージョン・ホスト名・モデル名は一次ソースの表記をそのまま使う**。取り違えは要約全体を無価値にする。（典型的な取り違え：モデル名の世代番号を1つ古く覚えている、ドメインの TLD を同じ会社の別サービスのものと混同している）

5. **曖昧さには2種類ある。「指しているものが実在するか」で切る。**

   - **5a. 対象が特定できない**（実在しない／聞き間違い／指すものが見つからない）
     確定させない。**型を不明型に切り替える**。近い候補を複数提示し、どこで見聞きしたか（チャット・記事・SNS など）を尋ねる。見つからなければ、確認日と確認した場所を添えて「見つからなかった」と書き（→ 最新性の照合の「存在しない」と書かない）、推測は推測として事実と分ける。
     例：製品 X の「v3」について聞かれたが、X は実在するのに v3 という版は見つからない。**5a**。

   - **5b. 実体はある。呼び名が複数の実体を指しうる、または正式名と違う**
     止めない。型はそのまま。実体を全て並べ、どこが違うかを書く（→ 出力形式の「似て非なるものは区別する」）。
     例：「製品 P の機能 F」と聞かれたが、P での正式名は G で、F は同じ開発元の別製品 Q の機能だった。どちらも実在する。**5b**。

## 情報源の序列

上ほど強い。衝突したら上が勝つ。段は**ホストではなく中身**で決まる。

```
公式ドキュメント・仕様・リリースノート
  ── 公開ページでも、その原本ファイル（リポジトリの docs/*.md、CHANGELOG.md 等）でも同格
  > 開発元リポジトリの README・ソースコード
  > 公式ブログ・開発者本人の発信
  > 一次情報に当たった署名記事
  > コミュニティのまとめ・Q&A
  > 無署名の解説記事
```

1段目と2段目の境界：**README がその機能の仕様説明そのものを兼ねていて、他に仕様書が存在しない場合は1段目**として扱ってよい。使い方の入口にすぎず別に仕様書がある場合は2段目。

**個人ブログを低く見ない。** 当事者の個人ブログは、検索上位のまとめ記事より上。

**弱いソースの症状**（ドメイン名ではなく本文で判定する）

- 元記事へのリンクがない／出典が「報道によると」止まり
- 具体値のない一般的な限定句ばかり
- 未来形の推測（〜する見込み、〜かもしれない）を既成事実のように書く
- 数値・日付の出典がない、記事自体に公開日がない
- 製品マーケティング文、または明らかにチェリーピックされた比較

**扱い**：症状のあるソースしか無い事実も落とさない。「〜という記述があるが一次ソース未確認」と分離して書く。ソースどうしが食い違ったら上の段を採り、食い違う記述があることも書く。

## 出力形式

**手順0で決めた型の欄だけを使う。他の型の形を混ぜない。**

チャット内で返す（ファイル化しない。明示の要望があれば別）。

最新版・現行の仕様・存在の有無を書くときは、確認日と確認元を本文に添える（例：「<日付>時点、npm レジストリで確認」）。

### 確認型

本文には見出しも箇条書きも使わない。問いに答えるのに要る長さの散文。

本文の**後ろ**に出典リストを置くのは規定に反しない（ツール側が Sources を要求することがある）。守るのは、本文の中に見出しや箇条書きを持ち込まないこと。

例（「X の最新バージョンいくつ？」に対して。値は形を示すための仮のもの）:

> X の最新は N.N.N（YYYY-MM-DD 時点、パッケージレジストリで確認）。N.N 系はパッチが継続的に出ている段階で、直近は〈変更の主題〉と〈領域〉まわりのバグ修正が中心。前のメジャーからの破壊的変更は見当たらない。なおリリース日そのものは、一次ソースからも明確な日付表記が拾えなかった。

### 比較型

比較軸の表 ＋ 所感。見出しは使わない。表に入らない前提や注意は、表の後に短く。

### 深掘り型

これは何か → できること／要点 → 注意点・前提 → 結論・所感。

この4節は `##` 見出しにしてよく、各節の中では箇条書き・表を使ってよい。ただし**この4つの並び自体を別の見出しで置き換えない**（内容ごとに見出しを立てて4節構成を崩さない）。

### 不明型

候補を列挙し、どこで見聞きしたかを尋ねて終わる。断定的な要約を書かない。

---

- フラットな日本語。絵文字なし。前置きや冗長な相槌なし。簡潔に。
- **似て非なるものは明確に区別する**（例：同じ製品名の MCP の2系統＝「その製品を AI から操作する側」と「その製品のアプリが外部 MCP を呼ぶ側」／同じ機能の2形態＝マネージド版と、自前の CI で動かす版）。5b に当たったときは必ずこれを行う。

## 環境文脈

**既定は「添えない」。** 利用者の環境との接続点があるときだけ添える。距離のない話題に接続文を付けると、毎回同じ定型句が並んでノイズになる。

利用者の環境は、メモリ・CLAUDE.md・この会話から分かる範囲で判断する。分からなければ添えない（環境を推測で補わない）。

**添える**：その技術を利用者の環境で使う／使わない判断に影響するとき。

- 特定のプラットフォーム前提のツール（特定の CI サービス専用の連携、特定ベンダーの CLI に依存する手順、特定のマーケットプレイス経由のみの配布）で、利用者がそのプラットフォームを使っていないと分かっているとき → 利用者の環境で同じことをするには何が必要で、何を失うかを書く。典型的には、提供元の API を直接叩く自前スクリプトを CI ジョブに組み込めば動作は再現できるが、連携設定の自動化という利便性は失われる。
- 利用者が使っていると分かっているサービスの競合・代替 → 乗り換えコストと、移らなくても真似できる点を書く

**省略する**：言語仕様・一般概念・資格体系など、環境に依らない話題。

- 例：TypeScript の `satisfies` 演算子の使い方 → 省略
- 例：Claude Code の skill と plugin の違い → 省略（ツール内部の話で、利用者の環境とのギャップが生じない）

**「利用者の環境には関係ない」「ギャップという概念自体が生じない」と書くのは省略ではない。** その場合は節ごと書かない。

## オプション（ゲート付き）

次は**コアではなく追加**。明確に有用なときだけ出す。

- 採用判断（入れるべきか）
- 利用者の環境への適合性の評価
- 代替ツール・サービスの比較

有用かどうか迷ったら、勝手に展開せず「採用観点／代替比較も出す？」と一言確認してから出す。

## 品質チェック（出す前に自問）

- 手順0で決めた型の出力形式だけを使ったか（深掘り型は4節の並びのまま）。
- 最新版・現行の仕様・存在の有無を、このセッションで取得した一次情報で照合し、確認日と確認元を添えたか。
- 環境文脈は、接続点があるときだけ添えたか。
